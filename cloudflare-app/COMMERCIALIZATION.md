# BitWorld 商业化与多账号方案

## 1. 产品边界

BitWorld 面向需要持续获取情报、组织 AI 分工并自动交付报告的个人经营者与小团队。商业化版本采用“一个登录账号，一个独立公司空间”的初始模型：

- 每个账号拥有独立的任务、运行记录、报告、审批、动态、Token 用量和定时任务。
- 每个账号独立配置 Telegram、飞书或企业微信，凭据加密保存，通知只发送到所属账号。
- Agent 岗位、模型分层与基础系统指令由平台维护，避免新用户从零配置；用户的实际执行和用量互不影响。
- 平台所有者负责公共 Agent 模板、AI 路由、账号停用与安全运维，不参与用户日常数据。

首版不引入复杂的企业组织、席位和权限树。后续需要多人协作时，再把“账号空间”升级为“工作区 + 成员”，不会破坏当前数据归属。

## 2. 首次使用路径

目标：新用户在 5 分钟内完成首次有效交付。

1. 使用 Google 或邮箱验证码注册，验证后立即获得独立空间。
2. 首页展示三步引导：连接消息渠道、创建定时任务、提交首个任务。
3. Telegram / 飞书配置只显示当前账号的数据，并提供连接测试。
4. 用户可直接使用平台预置的总部、新闻、舆情、加密和研究团队。
5. 任务完成后在消息渠道收到结论摘要和 PDF 文件，后台同步归档。

## 3. 数据隔离规则

以下表以 `user_id` 作为强制租户边界：

- `tasks`
- `goals`
- `reports`
- `approvals`
- `runs`
- `activity`
- `scheduled_tasks`
- `company_workflows`
- `bot_messages`
- `notification_channels`
- `usage_events`
- `account_settings`

所有面向登录用户的读取、更新和删除都必须同时包含资源 ID 与当前 `user_id`。不可只凭资源 ID 操作。公开 PDF 仅通过不可预测的下载令牌访问，令牌不出现在其他账号的后台接口中。

通知事件必须显式传入 `user_id`，禁止向全部已启用渠道广播。

## 4. 商业版本建议

### 体验版

- 1 个独立公司空间
- 公共 Agent 团队
- 手动任务与有限定时任务
- Telegram / 飞书任选一个渠道
- Cloudflare 免费模型优先，超出平台安全阈值时暂停或提示升级

### 专业版

- 更多定时任务和并发工作流
- Telegram 与飞书同时启用
- 更高的月度 Token 使用量
- 专题报告模板、历史检索和优先队列
- 自定义公司名称、时区和报告品牌

### 团队版（第二阶段）

- 工作区、成员邀请和角色权限
- 共享报告库与审批流
- 工作区级通知渠道和 Agent 配置
- 审计导出、数据保留策略和组织级用量

收费建议优先采用“订阅包含平台能力 + Token 使用量分档”，不直接展示模型成本细节。DeepSeek 与 Cloudflare 的实际支出由平台侧计量和风控。

## 5. 上线门槛

正式开放付费前必须完成：

- 自动化跨账号越权测试，覆盖读取、更新、删除、任务运行、报告下载和通知发送。
- 注册防滥用：邮箱频率限制、人机验证、账号级并发限制和异常用量封禁。
- 支付与订阅状态：套餐、账单、续费失败宽限期和停用策略。
- 数据治理：隐私政策、服务条款、数据导出、账号注销和保留周期。
- 运维：错误告警、队列积压、定时任务成功率、AI 提供方故障切换和每账号成本监控。
- 客服入口：配置诊断、任务失败重试和问题反馈。

## 6. 推进顺序

1. **隔离底座**：完成现有业务表、通知和用量的账号级隔离。
2. **自助开通**：注册即用、三步引导、用户自己的定时任务和渠道。
3. **封闭试用**：邀请 5–10 个真实用户，验证首次交付时间、报告质量和留存。
4. **计费风控**：接入订阅、套餐权益、并发限制和账号级成本保护。
5. **公开发布**：完善条款、注销、客服、监控与运营后台。
6. **团队工作区**：在单账号模型稳定后再增加成员协作，避免首版复杂化。

核心商业指标应以首次有效交付率、7 日内第二次使用率、定时任务持续启用率、报告打开率和付费转化率为主，而不是注册数或 Agent 数量。
